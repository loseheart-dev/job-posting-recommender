# 面向大学生求职的岗位数据分析与个性化推荐系统——调研报告

作者：卢世豪　学号：25051408　课程：软件开发实践1
撰写日期：2026-09-06　项目代码基线：`58a7a7a`

## 摘要

本报告围绕大学生求职中的岗位比较、技能准备和薪资理解问题，调研在线招聘产业应用、语义检索、招聘智能体、结构化分析与可解释推荐方法。资料来自企业官方技术文章、研究论文、开源项目和框架文档，并结合本项目实际数据复算评估技术选择。调研表明，招聘产品正向语义理解和工作流辅助发展，但数据质量、计算成本和结果可信度仍是落地关键。本项目使用 Python、pandas、scikit-learn、Streamlit 和 Plotly，以 TF-IDF 和多因素规则实现课程原型。当前具有分析与展示能力，尚未实现分布式处理、后台自动采集和经过校准的录用概率预测。

关键词：大学生就业；岗位数据；语义检索；多因素推荐；数据质量

## 一、调研背景、目标与方法

大学生选择实习或就业岗位时，需要同时比较职位名称、城市、学历、经验、技能和薪资。单条招聘信息容易阅读，但跨岗位归纳“需要学什么”“哪些岗位适合当前能力”“不同条件下的薪资如何变化”仍有整理成本。本项目希望把岗位信息转化为可比较的数据，并提供能够检查依据的分析结果。

本次调研回答三个问题：招聘行业如何应用数据与人工智能技术；哪些方法适合两周课程中的五人团队；系统应如何说明结果及其局限。采用官方文献查阅、开源工具分析、代码核对和本地数据复算，没有开展问卷、访谈或用户对照实验，因此用户需求属于项目场景分析，不宣称经过大规模用户调查。

资料检索日期为 2026-09-06，重点关注 2025—2026 年招聘应用进展，同时参考框架文档。企业材料用于确认公开披露的能力，不作为本项目效果证据；本地测试只说明指定输入下的行为。课程依据为[期末材料提交说明及教学大纲附件](https://n1jd22jdwvl.feishu.cn/wiki/F64zwGTXmiWtwwkInfqccaUcnxf)。

## 二、产业应用现状

### 2.1 国内招聘平台：沟通与推荐结合

BOSS 直聘官方介绍将直接沟通、推荐结果与人工智能、大数据能力共同作为产品特征[1]。其服务对象包含求职者与招聘者，目标覆盖人才发现及后续沟通。本项目围绕有限岗位样本进行清洗、分析和推荐，不提供聊天、简历投递或企业招聘管理，也不能从公开介绍推断其内部模型与权重。

BOSS 直聘的参考价值在于真实岗位字段和信息组织方式。来源真实不等于样本具有总体代表性：关键词、城市、采集时间、页面排序和访问限制都会影响数据分布。项目统计必须标注范围，不能把本地平均薪资解释为全国毕业生平均工资。

### 2.2 国际招聘应用：语义搜索与流程辅助

LinkedIn 于 2025 年发布的 Hiring Assistant 工程文章介绍了计划与执行结构、检索工具和人工验证数据的作用[2]。产业应用已不仅输出排序列表，还涉及搜索策略、候选人管理与交互流程。

2026 年论文《Semantic Search At LinkedIn》介绍了面向职位和人才搜索的框架，将向量检索、LLM 相关性判断与蒸馏后的小模型结合[3]。其启示是语义能力和工程效率需要共同设计，不能仅靠接入大模型解决全部搜索问题。本文据论文摘要确认技术路线，不将其所述收益移用于本项目。

### 2.3 本项目定位

| 对象 | 核心价值 | 可借鉴内容 | 本项目边界 |
|---|---|---|---|
| BOSS 直聘 | 岗位发现、沟通与匹配 | 岗位、城市及企业信息组织 | 限定来源岗位，不实现招聘交易流程 |
| LinkedIn 语义搜索 | 根据输入含义检索职位和人才 | 语义召回、相关性评价、效率优化 | 当前是字符 TF-IDF，未部署向量模型 |
| LinkedIn Hiring Assistant | 辅助完成多步骤招聘工作 | 工具调用与人工评估结合 | 不自动筛人、联系候选人或作招聘决策 |
| Career Signal | 理解样本市场与自身技能差距 | 来源、统计口径、推荐理由可检查 | 单机课程原型，尚需用户评价 |

## 三、相关技术路线与发展趋势

### 3.1 文本匹配：从词面重合到语义表示

TF-IDF 根据词项在文档和语料中的分布表示文本，适合建立低成本检索基线[4]。本项目使用字符二元、三元片段及余弦相似度，避免仅按空格拆分中文职位名。优势是无需外部模型服务，评分过程易复现；不足是不能稳定理解同义表达、隐含经验和复杂项目经历。

Sentence Transformers 文档提供文本嵌入、相似度和重排序能力[5]；LinkedIn 的研究展示了这些能力与生产检索结合的方向[3]。据此，后续可以实验“规则筛选＋向量召回＋重排序”，但应先建立人工标注的岗位相关性样例，再比较 Precision@K、NDCG@K、响应时间和资源消耗。没有评价集，模型升级不能证明推荐更好。

### 3.2 结构化分析：统计解释与预测分开

随机森林组合多棵树进行预测，适合结构化特征建模[6]。本项目用学历、经验、城市、技能等特征预测标准月薪，并保留测试集指标。薪资因素分析采用分组统计，说明不同条件对应的样本差异。预测误差评价拟合能力，分组差异描述样本结构，二者都不能证明某因素导致薪资变化。

项目还用 KMeans 观察岗位群组，用技能共现描述同一岗位中的技能关系。聚类编号不是职业等级，共现关系也不等于完整的职业知识推理系统，结论需要结合输入和特征解释。

### 3.3 数据处理：单机原型与分布式能力

Spark SQL 和 DataFrame 提供结构化数据处理接口[7]。数据量、并行任务或内存限制成为瓶颈时，可以考虑分布式处理。当前实现使用 pandas，处理约两万条记录。项目分工提出过 PySpark/Spark 要求，但代码和依赖尚无对应实现。Spark 是仍需完成或与教师确认调整的需求，不能以“已有 pandas”表述为完成大数据组件验收。

### 3.4 交互与解释：让用户理解结果

Streamlit 的脚本重运行、表单和会话状态机制适合以 Python 实现数据应用[8]。本项目用表单集中提交筛选和画像，用图表展示分布，并提供推荐理由与匹配、缺失技能。这减少了前后端联调成本，但多用户持久化、复杂权限和持续后台任务仍需额外设计。

解释应回答“结果能帮助我做什么”：技能频率用于准备学习内容，岗位薪资用于比较招聘条件，推荐分数用于排序参考。界面的“匹配概率”没有录用标签和概率校准依据，其实际含义是组合评分，不是收到录用通知的可能性。

## 四、方案比较与选择依据

| 环节 | 候选方案 | 当前选择及理由 | 主要限制 |
|---|---|---|---|
| 数据获取 | 自建解析、开源采集器、授权接口 | 固定采集器版本，自行适配、遍历和清洗[9] | 访问受限须停止，来源稳定性受平台影响 |
| 数据处理 | pandas、Spark DataFrame | pandas 已形成可运行链路，便于检查字段 | Spark 要求尚未完成 |
| 岗位推荐 | 关键词、TF-IDF＋规则、向量模型 | TF-IDF＋技能和城市等因素，加分依据可解释 | 人工权重，缺乏相关性评价集 |
| 薪资分析 | 分组统计、随机森林、更复杂模型 | 分别承担解释与预测验证 | 字段缺失、薪资长尾，不承诺精准待遇 |
| 页面 | Streamlit、独立前后端 | 复用 Python 技术栈形成五模块应用 | 无账号隔离和后台任务执行 |

项目复用开源采集能力，自行完成字段统一、薪资规则、任务遍历和业务分析。固定版本与 commit 见[采集基线](../BOSS直聘采集基线.md)，不能把上游已有功能作为个人独立开发成果。

## 五、结合实际数据的调研判断

2026-09-06 对本机标准表复算：20,872 条岗位，32 个城市，岗位 ID 无重复；19,807 条有效月薪，占 94.90%，1,065 条薪资缺失或不可按当前规则解析。有效月薪均值 10,335.58 元，随机森林 MAE 为 3,897.09 元、R² 为 0.2019。输入摘要与结果见[本次验证记录](assets/报告验证-20260906.json)。

结果支持“可以对样本进行分析”，不支持“可以准确预测个人待遇”。岗位描述缺失 20,796 条，公司介绍、公司性质、工作类型均整列缺失，文本匹配主要依赖标题、技能和公司名称，企业画像不能补造字段。技术类占 33.61%，各类别采集量不一致；类别等权统计只能缓解大类占比影响，不能消除采样偏差。

下一步首先应改善来源允许范围内的字段完整性和样本评价，再评估复杂模型。没有录用结果，不能报告推荐准确率、录用率或就业成功率提升；没有连续历史快照，也不能绘制真实招聘趋势。

## 六、思政心得：把技术责任落实到具体实现

> 本节为结合项目事实拟写的心得初稿，提交前需由本人阅读并按真实理解修订。

我对工程服务社会的理解，首先落在减少信息理解门槛上。大学生需要的不只是更多岗位，还需要知道技能对应什么需求、薪资数字来自什么样本。把来源、单位和限制说清楚，是技术帮助就业选择的前提。科技报国不只体现在使用新模型，也体现在认真解决身边的问题，让工具对使用者有用、可信、可解释。

薪资清洗使我认识到，细节会改变结论。把日薪按假定工作日换算成月薪，或为使指标好看而删除合法高薪，都会影响同学对待遇的判断。本项目保留原文，只对明确人民币月薪填入数值，对不能统一的记录留空。诚实守信体现为保留不完整、不理想的结果，而不是把报告写成没有问题的展示材料。

团队合作要求尊重职责和证据。组长负责分工、接口协调和审核，不能把成员完成的算法与页面全部归为个人成果。使用开源项目应保留来源，使用 AI 辅助应由开发者检查、运行并解释结果。访问受限时停止并记录，不能为数量绕过限制；模型有误差时分析原因，不能把规则分数包装成录用概率。

持续学习应以问题为出发点。语义搜索和招聘智能体值得学习，但采用前应说明它解决什么问题、如何验证、增加什么成本。对数据和使用者负责、尊重协作成果、实事求是，是本次实践中需要继续落实的工程习惯。

## 七、结论

招聘信息服务呈现语义检索、模型与工具协同、结果解释等方向。本项目用有限真实样本建立可解释原型，TF-IDF、规则评分和传统机器学习具有易检查、可复现的优势。后续优先补齐数据质量和验收缺口、建立人工相关性评价，再在证据支持下升级模型；前沿技术调研不等于已经完成功能。
