# 调研报告

> 课程：软件开发实践1（S0512331）　成员：徐挚凌（25051430）
> 项目：面向大学生求职的岗位数据分析与个性化推荐系统

## 一、调研背景与目的

本项目面向实习和校招大学生，解决三个具体问题：岗位信息分散、待遇难以横向比较、求职方向难以判断。团队首期采集 BOSS 直聘的大数据相关岗位，形成“采集—清洗—分析—推荐—展示”的完整链路。我在团队中负责后端服务与调度，动手之前必须先弄清楚几件事：岗位数据从哪来、如何清洗、用什么方法分析、推荐怎么做，以及这些技术目前发展到什么程度。带着这些问题，我对网络数据采集、大数据处理、文本表示、机器学习与推荐、低代码可视化五个方向做了调研，并结合课程“科技报国”的要求写下心得。

## 二、相关领域前沿技术发展趋势

### 1. 网络数据采集：从手工解析走向浏览器协议驱动

招聘岗位数据分散在各平台的动态页面上，传统做法是用 Requests 直接请求接口或解析 HTML，遇到前端渲染、登录态和验证码就失效。近年的一个方向是借助 Chrome DevTools Protocol 被动读取页面自身返回的数据，也就是浏览器已经拿到什么就取什么，不额外拼接口。本团队固定 `boss-zhipin-scraper` 的 `v2.2.0` 版本，在独立 Chrome 用户目录中由使用者手动登录，再自研 BFS/DFS 组织关键词、城市和任务的遍历，把“如何稳定取数”和“按什么顺序取数”分开处理。

### 2. 大数据处理：从单机 pandas 到 PySpark

单机 pandas 在课程规模的数据上足够，但当岗位表达到数十万行、需要重复清洗和多轮聚合时，内存和耗时都会受限。行业里普遍把 PySpark/Spark DataFrame 作为规模化方案。本项目当前的清洗、服务、算法和页面均使用 pandas；PySpark/Spark DataFrame 是接口约定中的后续扩展方向，尚未加入当前依赖或代码。后续若引入 Spark，仍需把结果转换为固定的 21 列岗位表和返回结构，避免上层模块被处理引擎绑架。

### 3. 文本表示与信息提取：从 TF-IDF 到预训练模型

岗位的“技能”字段本质是短文本，需要转成可计算的向量才能做匹配。TF-IDF 是代价最低、可解释性最好的起步方案，本项目的推荐基线就用 `char_wb` n-gram 的 TF-IDF 加余弦相似度。再往上是词向量、BERT 等预训练模型，表达能力强但依赖算力和语料，课程原型阶段并不划算。调研后我们确定：先用 TF-IDF 打通链路，把模型接口和输出列冻结，未来若换更强的文本模型，只替换算法层即可。

### 4. 机器学习与推荐系统：可解释优先

推荐系统的主流路线分为内容过滤、协同过滤和混合推荐，工业系统还叠加召回—粗排—精排的漏斗。本项目没有用户行为日志，无法做协同过滤，因此选择“内容 + 多因素评分”：TF-IDF 计算文本相似度，学历、城市、经验、薪资区间等因素参与综合打分，输出匹配概率和推荐理由。聚类用 KMeans 做岗位分组，薪资预测用随机森林回归，两条都要求可解释——KMeans 输出群组说明，随机森林输出 MAE 与 R² 指标，而不是只给一个“黑箱分数”。

### 5. 低代码与生成式 AI 对招聘场景的渗透

招聘平台近年普遍引入大语言模型做职位描述润色、简历解析和人岗匹配，猎聘、BOSS 直聘等也把 AI 摘要、AI 面试列入产品。这些能力降低了使用门槛，但也带来两个问题：一是推荐依据更不透明，用户难判断排序理由；二是自动采集与个人信息处理必须守住合规边界。本项目的定位正好回应第一点——不追求“黑箱匹配”，而是把薪资因素、能力图谱、企业画像和推荐理由显式地摊开给用户看。

## 三、产业应用现状

| 调研对象 | 主要功能 | 数据与技术特点 | 对本项目的参考价值 |
|---|---|---|---|
| BOSS直聘 | 职位搜索、企业查看、校招、求职者与招聘方直接沟通 | 按职位、城市、行业组织岗位，推荐与匹配规则未公开 | 作为首期数据来源，重点分析技能、薪资和企业信息 |
| 智联招聘 | 校招、实习、职位搜索、简历投递 | 岗位通常含职位、地区、学历、经验和企业信息 | 作为后续扩展平台，用于比较不同平台的岗位差异 |
| 前程无忧（51job） | 全职、实习、校招、职位搜索与投递 | 覆盖职位、薪资、地区、经验、企业等信息 | 作为后续扩展平台与数据对比对象 |

三个平台都能完成搜索，也都在做推荐，但排序依据几乎都不公开。用户看到的是“推荐岗位”，却看不到“为什么推荐”。本项目不复制聊天和投递功能，而是把限定范围的公开岗位信息统一字段后，把分析过程做成可见的结果。数据层面只处理岗位信息，不采集简历、手机号、Cookie 等个人敏感信息；采集受登录、验证码和平台访问规则影响时保留真实记录，不绕过限制。

## 四、调研结论与技术选型

调研得到三条结论。其一，数据入口选 BOSS 直聘是合适的：上游项目提供了可复现的浏览器取数方式，团队自研遍历和清洗即可，无需从零开发采集器。其二，当前技术栈控制在课程已涉及或容易掌握的范围内——Python + pandas + scikit-learn + Streamlit，TF-IDF、KMeans、随机森林都足够支撑原型且可解释；PySpark/Spark DataFrame 保留为后续规模化扩展方向。其三，架构上把“采集、数据、分析服务、展示”分层，页面只调用服务函数、不直接读原始数据，既方便测试复用，也把每个人的分工边界划清楚。这些结论最终落到《接口约定》和具体代码里，成为团队并行开发的依据。

## 五、思政心得

调研过程中，我对“科技报国”有了比口号更具体的理解。招聘直接关系就业这个最大的民生问题，岗位数据的清洗和分析看似是写代码，实际是在帮学生把零散的招聘信息变成可比较、可判断的依据。把一件小事做扎实，本身就是工程技术服务社会的一种方式，这比空谈使命感更有说服力。

我在联调中反复修过 `salary_distribution` 的分桶边界：`numpy.histogram` 末桶右闭，会让恰好落在 5000 元整数倍的薪资被多算进前一个桶。这个问题不解决，图照样能画出来，但数字是错的。为了一个边界多写几个测试、多改一版，就是我对“工匠精神”和“诚实守信”的体会——数据和分析结果要经得起复查，宁可把问题暴露出来，也不能用看似正常的输出糊弄过去。

数据合规的一面同样提醒我：自动采集不等于可以随意抓取。团队约定不绕过登录与验证码、不保存账号 Cookie、不采集个人敏感信息，遇到平台限制就停手并记录原因。技术有边界，创新要在规则之内，这既是对平台的尊重，也是工程人员应有的法治意识。今后我仍会保持对新工具的持续学习，但更看重把每一步做对、把每一个结论讲清楚。
