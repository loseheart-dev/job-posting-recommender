# 设计报告

> 课程：软件开发实践1（S0512331）　成员：徐挚凌（25051430）
> 项目：面向大学生求职的岗位数据分析与个性化推荐系统

## 一、需求分析

项目面向实习和校招大学生，解决岗位信息分散、待遇难比较、求职方向难判断的问题。团队把需求拆成十则用户故事，其中与我职责直接相关的有四类：一是管理员可以增删改查招聘网站配置，设置采集开始时间和频率；二是管理员可以触发采集任务并查看状态、计数和错误信息；三是用户可以按关键词、城市、学历、经验、工作方式、行业、公司性质和薪资范围筛选岗位，并查看数量、技能和薪资分布统计；四是用户提交求职者画像后，系统返回分析和推荐结果。非功能上，系统要求采集失败、数据为空、筛选无结果、模型未加载时页面给出明确提示而非崩溃，且页面不得直接读取原始数据。

## 二、系统总体架构

系统采用“采集—数据—分析服务—展示”四层，各层只依赖相邻层的固定接口：

```text
采集层：网站列表管理、采集调度、BFS/DFS 遍历、BOSS 适配器
   ↓
数据层：BOSS 岗位数据 → 原始数据 → 清洗后 jobs.csv、数据字典
   ↓
分析服务层：岗位读取/筛选/统计、三类主题分析、KMeans、随机森林、多因素推荐
   ↓
展示层：Streamlit 管理页面、岗位检索、统计图表、画像分析、推荐结果
```

这个分层的意义在于把“谁负责什么”变成“谁依赖什么”。页面只调用服务函数，不直接读 `jobs.csv`，也不直接 import `src.algorithms`；算法模块只接收清洗后的表，不读文件、不碰 Streamlit。这样五个成员可以在冻结接口下并行开发，联调时只需核对函数签名和返回结构。

## 三、模块设计

### 1. 网站配置服务 `site_service`

用 `SiteConfig` 数据类承载 `site_id / site_name / base_url / enabled / keywords / cities / crawl_strategy / start_at / frequency / max_depth` 十个字段，提供增删改查、启停和默认站点补齐。校验规则集中在 `from_mapping`：`site_id / site_name / base_url` 必填，`crawl_strategy` 只能是 `bfs/dfs`，`frequency` 只能是 `once/daily/twice_daily`，`max_depth` 不能为负。存储采用内存态单进程字典，不引入数据库或后端框架，符合课程项目的轻量定位。

### 2. 采集任务调度 `task_service`

`CollectionTask` 记录 `task_id / site_id / started_at / finished_at / status / raw_count / parsed_count / error_count / error_message`。`trigger_task` 校验站点存在且启用后生成 `pending` 任务；`update_task` 限定可更新字段并校验 `status` 枚举和计数非负。调度不引入真实后台定时器，`compute_next_run` 只做纯计算——`once` 返回空，`daily` 取 `start_at` 时分，`twice_daily` 在该时分与加 12 小时各一次，最多向后找 8 天，保证任意时刻都能算出一个合理的下次计划时间。

### 3. 数据读取、筛选与统计

`load_jobs` 读取 21 列标准岗位表，缺文件返回空表、缺必填字段抛错。`filter_jobs` 支持 9 个筛选键，对关键词做文本包含匹配、对薪资区间做边界比较，返回标准列且不修改输入。`summarize_jobs` 返回 `job_count / salary_count / salary_min / salary_max / salary_avg / top_skills` 六个固定键。`salary_distribution` 是我新增的独立函数，按 `salary_avg` 以 `step`（默认 5000 元）分桶，桶边界严格左闭右开。

### 4. 算法调用适配 `analysis_service`

这是我在设计上最看重的部分。郑维豪的三类分析/KMeans/随机森林与丁伟哲的推荐各自有独立函数签名和返回结构，如果页面逐个直接 import，会重复写模型逻辑，接口一改就多处失效。我把七类能力统一收口到 `analysis_service`：`salary_factor_analysis / salary_prediction / job_cluster / skill_graph / company_profile / recommend_jobs / recommend_jobs_multifactor`，并统一空数据契约——分析类空表抛中文 `ValueError`，推荐类空表/空画像返回空结果表不抛错，页面按“无推荐结果”处理。

## 四、数据设计

岗位表固定 21 列（`JOB_COLUMNS`），其中 `job_id / title / company / skills / salary_min / salary_max / salary_avg / source / crawled_at` 九列必填，其余如 `company_intro / company_nature / work_type` 等无稳定来源的字段保留缺失标记、不从其他字段推断。薪资统一为人民币元/月，无法解析的“面议”不填 0。求职者画像 `StudentProfile` 固定 11 个字段，其中 `experience` 作为兼容字段用于匹配岗位表经验要求，字典输入时技能字符串按英文分号拆分。这些字段全部冻结在《接口约定》和 `src/data/schema.py`，五个分支共用，不允许各自改名。

## 五、接口设计

服务层接口只暴露少数稳定函数：`filter_jobs / summarize_jobs / salary_distribution` 以及 `analysis_service` 的七个函数。设计上有两个关键决定。其一，`summarize_jobs` 是冻结接口，返回键固定，我没有往里塞“薪资分布”，而是新增独立函数 `salary_distribution`，既满足需求又不破坏已有调用。其二，空数据语义按函数性质区分：筛选、统计和推荐返回空结果，分析类抛出明确错误，页面据此分别渲染“无结果”或“数据为空”。这份契约同步写在模块 docstring、测试和《服务层调用说明》三处，避免三处不一致。

## 六、关键技术选型与理由

技术栈选 Python + pandas + PySpark/Spark + scikit-learn + Streamlit。理由有三：一是都在课程已涉及或容易掌握的范围内，学习成本可控；二是 TF-IDF、KMeans、随机森林都具备可解释性，能输出推荐理由和评价指标，而不是黑箱分数；三是 Streamlit 用函数调用即可完成页面，不必为“像后端”而额外搭建 FastAPI 或数据库。数据采集参考上游 `boss-zhipin-scraper`，团队自研 BFS/DFS 与清洗，复用了成熟工具又保留了自研部分。

## 七、测试与验证

验证分四层。冒烟测试 `tests/smoke.py` 锁定服务契约；`verify_real_data.py` 用真实清洗结果（8608 行、61 个关键词、32 个城市）逐键断言读取、筛选、统计与分桶，并校验 `salary_distribution` 桶计数总和等于 `salary_count` 才自洽；`test_analysis_service.py` 覆盖七个函数的正常与空数据案例；`verify_app_integration.py` 用 Streamlit AppTest 驱动五个页面模块的真实交互并断言预期结果，同时检查 `at.error` 与非预期 `at.warning`，已纳入 CI 回归。调试中最典型的是分桶边界问题：`numpy.histogram` 末桶右闭会让恰好命中 5000 元整数倍的薪资被多算进前一个桶，我把末边改成严格大于最大值，并补了“恰好命中桶上界”的测试。

## 八、总结

这份设计把“采集、数据、分析服务、展示”四层用固定接口接起来，重点解决了页面如何稳定取数、算法如何统一收口、空数据如何统一处理三个问题。与我在调研报告中的判断一致：技术栈保持轻量和可解释，架构上以接口契约为边界，让五个人能在各自分支独立开发、最终顺利联调。
