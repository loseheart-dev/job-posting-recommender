## 一、项目概述与设计目标

本项目以 Career Signal 为页面名称，面向大学生的实习与就业信息理解需求，提供市场概览、岗位检索、分析洞察、个性化推荐和采集管理五个入口。核心目标是把来源有限、格式不统一的招聘岗位转换为标准数据，使用户能够比较岗位、理解技能需求并查看推荐依据。

报告按照[期末材料提交说明及教学大纲](https://n1jd22jdwvl.feishu.cn/wiki/F64zwGTXmiWtwwkInfqccaUcnxf)组织，覆盖需求、方案选择、数据结构、模块、交互、实验结果与思考。本报告描述当前实际实现；最初设计但尚未落地的内容单独列明，不以计划代替成果。技术调研和外部参考文献见[调研报告](调研报告.md)。

## 二、需求分析与验收边界

### 2.1 用户与使用场景

学生用户希望根据目标岗位、技能和城市缩小岗位范围，并了解薪资、企业规模和技能差距。例如，输入“数据分析师”和“Python;SQL”后，应得到实际候选岗位及其匹配理由；筛选无结果时应提示调整条件。管理员需要维护站点与任务配置，查看记录和错误；现有界面中的管理员是一种使用场景，尚未实现角色认证和权限隔离。

### 2.2 功能需求

| 编号 | 需求 | 当前实现与验收边界 |
|---|---|---|

## 三、总体架构与技术方案

### 3.1 分层结构

```text
独立 Chrome 与固定版本 BOSS 上游工具
                  │ 命令行任务执行、保存原始结果
                  ▼
scripts/run_boss_tasks.py ＋ src/data/traversal.py
                  │ JSON / CSV、JSONL 遍历记录
                  ▼
boss_adapter.py → cleaner.py → data/processed/jobs.csv
                                      │
                                      ▼
                              loader.py / job_service.py
                                      │
                    ┌─────────────────┴──────────────────┐
                    ▼                                    ▼
          analysis_service.py                  统计、筛选、分页
                    │                                    │
                    ▼                                    │
          src/algorithms/                                │
                    └─────────────────┬──────────────────┘
                                      ▼
                         app.py → src/ui/pages.py

采集管理页面 ↔ site_service.py / task_service.py（内存配置与记录）
该管理路径尚未连接到上方命令行执行器，无后台自动采集闭环。
```

数据层负责读取和清洗，服务层负责筛选及算法调用，算法层接收 DataFrame 和画像，不读原始文件、不调用 Streamlit，页面负责输入、图表与结果解释。实际入口由 `app.py` 调用 `load_jobs` 后将岗位表传给 `render_home`。

### 3.2 技术选择

| 技术 | 实际用途 | 选择理由与限制 |
|---|---|---|
| Python | 采集适配、处理、服务、算法与页面 | 同一语言减少接口转换，便于五人协作 |
| pandas、NumPy | 表格清洗、筛选、统计和数值计算 | 当前样本可在单机处理；并不等于分布式能力 |
| scikit-learn | TF-IDF、KMeans、随机森林、评价指标 | 复用成熟算法接口；效果仍受特征和数据影响 |
| Streamlit、Plotly | 表单、图表、分页及推荐展示 | 快速形成可操作原型；复杂权限和后台执行需另行实现 |
| CSV、JSON、JSONL | 标准岗位、原始结果和追加记录 | 易检查与交接；站点、管理任务目前另存于内存 |

运行依赖范围以[requirements.txt](../../requirements.txt)为准，不把在线文档版本视为本地安装版本。未引入独立前端框架、关系数据库、向量数据库或 LLM 服务。Spark 虽在原计划中提出，当前依赖和业务代码未接入，须在最终验收时说明。

## 四、数据结构与存储设计

### 4.1 标准岗位表

标准字段定义位于 [schema.py](../../src/data/schema.py)，详细来源见[岗位数据字典](../岗位数据字典.md)。当前数据存储采用 CSV，没有已经建成的关系数据库；以下是实际逻辑数据模型。

| 字段组 | 字段 | 类型及约束 |
|---|---|---|
| 标识与岗位 | `job_id`、`title` | 字符串；清洗后岗位 ID 唯一 |
| 企业 | `company`、`company_intro`、`company_size`、`company_nature`、`industry` | 字符串；无来源不推测 |
| 工作条件 | `city`、`work_type`、`experience`、`education` | 城市标准化，其他按来源保存与规范化 |
| 能力与内容 | `skills`、`description`、`benefits` | 技能、福利统一分号分隔；描述缺失允许为空 |
| 薪资 | `salary_text`、`salary_min`、`salary_max`、`salary_avg` | 保留原文；数值单位为人民币元/月，无法解析留空 |
| 来源 | `source`、`source_url`、`crawled_at` | 平台、来源链接和 ISO 8601 时间，供追溯 |

`crawled_at` 按适配器导入时写入，不能自动等同于招聘平台岗位发布时间。后续若需要岗位增量、时效判断或趋势，应先增加稳定的发布时间或历史快照设计。

### 4.2 画像与管理对象

`StudentProfile` 接收目标岗位、学历、专业、学校、技能、期望城市、经验状态、工作年限、工作经历及期望月薪上下限。当前多因素评分直接使用目标岗位、技能、城市、经验状态、学历、专业和薪资；学校、工作年限和工作经历主要进入理由说明，不能声称这些字段均已参与数值排序。

`SiteConfig` 保存站点 ID、名称、URL、启停、关键词、城市、BFS/DFS、开始时间、频率和最大深度。`CollectionTask` 保存任务 ID、站点 ID、开始/结束时间、状态、原始数、解析数、错误数及错误信息。管理对象分别保存在进程内字典 `_SITES` 和 `_TASKS` 中，重启后不保证保留。

若后续需要持久化，应先明确站点与任务生命周期，再用数据库建立站点主键、任务主键和站点关联。该方案是后续设计，当前没有数据库表、事务或跨进程调度实现。

### 4.3 数据质量规则

原始数据先保存，再映射标准列和清洗；岗位 ID 去重，标签统一分隔，城市去除区县商圈后缀。薪资以 `salary_text` 为依据，只解析明确人民币月薪；日薪、时薪、年薪、面议及单位不明数据保留原文，三个薪资数值字段置空，不以 0 代替缺失，不按假定工时换算。

明确高月薪予以保留，算法侧只保留低于 500 元/月的历史污染兜底标记。不得恢复超过 10 万元硬删除规则。本次复算检查高薪未被标记、薪资分桶计数等于有效薪资数量；单元测试检查非月薪清空等正常及异常输入。

## 五、核心模块与算法设计

### 5.1 采集、遍历与清洗

上游固定为 `v2.2.0`，commit 为 `2bc40f56a3ca3249ce3b98cdda0187e0bd612aa5`，来源与复现记录见[采集基线](../BOSS直聘采集基线.md)。用户在独立浏览器中手动登录，执行器按关键词、城市调用上游，再由适配器和清洗函数输出标准数据。平台出现验证或访问限制时停止，不绕过限制。

自研 `traverse_tasks` 使用双端队列组织任务：BFS 从队首取节点，DFS 从队尾取节点，结合已访问键和深度上限避免重复与无限扩展。`visit` 返回结果数量和子任务，过程可追加到 JSONL。当前真实采集生成平铺根任务，上游一次处理指定页数，没有子任务时两种策略访问顺序相同；带子任务的单元测试才验证 BFS/DFS 差异，不能把平铺采集记录说成完整网站图遍历证明。

### 5.2 服务与异常接口

| 接口 | 输入与输出 | 异常或空数据行为 |
|---|---|---|
| `load_jobs` | CSV 路径 → 标准 DataFrame | 缺文件返回标准空表；空文件、缺必要列抛明确错误 |
| `filter_jobs` | 岗位表＋条件 → 筛选表 | 无结果返回空表；不修改原输入 |
| `paginate_jobs` | 筛选表、页码、页大小 → 数据及总数 | 处理空结果及越界页码 |
| `salary_distribution` | 岗位表＋桶宽 → 分桶列表 | 无有效月薪返回空列表；非法桶宽报错 |
| `analysis_service` | 岗位表 → 分析表或字典 | 分析类空数据抛错误，页面相应区域处理 |
| `recommend_jobs_multifactor` | 画像、岗位表、Top-K → 推荐表 | 空画像或空岗位返回标准空结果 |

入口 `app.py` 直接调用加载器，当前没有包裹加载异常；因此不能把“加载器能给出明确错误”写成“所有文件错误均已在页面优雅处理”。缺文件空状态与文件损坏报错需要分开说明。

### 5.3 多因素推荐

当前页面主用评分为：

```text
S = 0.35 × 文本余弦相似度 + 0.25 × 技能 F1
  + 0.10 × 城市命中 + 0.05 × 经验命中
  + 0.05 × 学历命中 + 0.05 × 专业命中
  + 0.15 × 期望与岗位薪资区间重叠
```

文本相似度比较目标岗位与岗位标题、技能、描述、公司组合文本，使用 `char_wb` 二至三元 TF-IDF。技能 F1 同时考虑已掌握技能覆盖和岗位技能匹配，避免仅凭一个共同技能得高分。城市、经验、学历和专业采用当前代码的文本命中规则，属于可解释基线，不是完整资格判断；例如学历命中没有建立学历高低的完整可接受关系。

候选岗位优先按目标岗位名称族限制；数量不足时尝试识别的岗位类别，再不足则保留全集进行评分。按组合分降序取 Top-K，返回公司、薪资区间、匹配技能、缺失技能与理由。权重是人工设置的，未用录用标签训练。`match_probability` 为限制在 0—1 的组合分，未经过概率校准，不能当作录用概率；`salary_range` 来自岗位薪资上下限，不是针对个人训练出的置信区间。

### 5.4 三类分析、聚类与预测

薪资因素模块对学历、经验、城市、企业属性等可用字段分组，统计平均月薪和样本数。方向依据相对整体均值的差异判定，重要性来自组间加权离散程度归一化，并非随机森林特征重要性，也未进行因果推断。

技能图谱以技能为节点，同岗位共现为边，并提供频率与类别等权统计。技能白名单和别名有助于减少“要求经验”等标签噪声，也可能遗漏新技能。企业画像汇总实际公司的规模、性质、行业、薪资和技能；缺少性质或介绍时保留缺失，不把企业规模当作性质推断。

KMeans 对编码后特征标准化，默认分 3 类，`random_state=42`、`n_init=10`，返回 `cluster_id` 及群组人数、薪资和代表特征。群组数是默认参数，当前没有证明其为最优分类，也没有监督学习意义上的聚类准确率。

随机森林使用不含薪资目标列的技能、学历、经验、城市及企业属性编码，100 棵树，随机种子 42，训练/测试比例 7:3；标准化器在训练集拟合。MAE 衡量月薪平均绝对误差，R² 衡量当前测试集上的拟合表现。编码特征集合在划分前由全表构建，且未按公司或时间隔离，因此此次结果不是严格时间外推或新公司泛化评价。模型对全表给出的预测列包含训练样本，不能用全表误差替代测试集指标。

## 六、界面与交互设计

采用浅色背景、左侧五模块导航和右侧工作区。蓝色表示主要操作，绿色用于匹配与正常状态，橙色突出薪资。使用文字标签、单位、图例及空状态，避免单靠颜色传递含义。视觉规范和历史设计稿见[前端设计说明](../团队/前端设计说明.md)；设计稿中的数字不作为实验截图或实际结果。

| 页面 | 用户操作 | 返回与解释 |
|---|---|---|
| 市场概览 | 查看样本范围及分布 | 岗位数、薪资覆盖率、技能与城市/学历分布，说明样本含义 |
| 岗位检索 | 输入条件、搜索、翻页、下载 | 实际结果数量、岗位详情、当前筛选 CSV；无结果提示放宽条件 |
| 分析洞察 | 选择分析主题或条件 | 薪资因素、技能共现、企业画像、聚类、MAE/R²与局限 |
| 个性化推荐 | 填写画像并提交 | 岗位列表、组合分、薪资、技能差距与理由 |
| 采集管理 | 维护配置、启停、触发任务 | 站点和内存任务记录；触发不代表实际在线采集完成 |

筛选与画像通过表单提交，推荐结果放在当前会话状态中；筛选变更时重置分页。系统没有收藏、简历投递、用户账户和真实历史趋势数据，不应在演示中暗示这些功能存在。
